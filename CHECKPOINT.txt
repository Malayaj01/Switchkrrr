Switchkrr Checkpoint
====================
Last updated: 2026-08-16

Where we are right now
----------------------
- Product direction is finalized: Switchkrr is a mentor-led job switching platform.
- Stack in place and working:
  - Next.js 16 (App Router, Turbopack, typedRoutes)
  - TypeScript
  - Prisma 6 + PostgreSQL
  - Signed HTTP-only session auth (jose + hashed session tokens)
- Local PostgreSQL now runs via Docker (`docker compose up -d`).
  Docker Desktop is installed on this machine; the daemon must be running.
- Prisma migrations are in place; `npm run db:deploy` and `npm run db:seed` work.
- Typecheck and production build both pass.
- App verified running at http://127.0.0.1:3001 with real data.

What is built and verified
--------------------------
Auth
- Signup (candidate + mentor), login, logout, current-user API.
- Role-aware routing and redirects on every dashboard page.

Candidate
- Profile completion form and API.
- Mentor discovery with anonymised previews (no name/company/LinkedIn exposed).
- Mentor request creation, with limits enforced:
  max 10 pending requests and max 5 active Hustles per candidate.
- Requests page showing pending and decided requests.
- Candidate dashboard: active Hustle summary, latest leads, upcoming
  follow-ups (overdue / due today / upcoming), request statuses, next action,
  and profile completeness.

Mentor
- Request review queue with approve/decline; approval auto-creates a Hustle.
- Capacity enforced at 10 active candidates, and approvals are blocked at the cap.
- Mentor dashboard: pending requests, active Hustles, candidate progress table,
  lead counts, follow-ups due, capacity bar, next action, recent lead movement.
- Read-only mentor profile page showing verification status and admin notes.

Admin
- Admin dashboard: total users, candidates, mentors, pending verifications,
  active Hustles, total leads, leads-by-status breakdown, and a merged
  recent-activity feed (signups + requests + progress updates).
- Mentor verification page at /dashboard/admin/mentors with status filters
  (Pending / Verified / Rejected / All) and search across name, email,
  company, domain and mentor code.
- Approve / reject / reset-to-pending, with an optional note.
- Verification is enforced, not cosmetic: REJECTED mentors are hidden from
  candidate recommendations and cannot receive new requests.
- Audit trail stored on MentorProfile: verifiedAt, verifiedById, verificationNote.

Hustle workspace
- Lead board with priority ordering, lead creation (mentor), status updates
  (candidate), comments, follow-up dates and full progress history.

Navigation
- Shared DashboardNav with active-route highlighting, role-filtered items:
  Dashboard, Profile, Find mentors, Requests, Hustles, Admin.
- Shared DashboardShell/MetricGrid/Panel components used by every page.

What is pending
---------------
- Mentor profile editing (mentors can view but not edit their profile).
- Candidate cannot cancel a sent mentor request (MentorRequestStatus.CANCELLED
  exists in the schema but no API or UI uses it).
- No automated test suite. Verification was done with manual smoke scripts.
- Pagination: the admin mentor list is capped at 50 rows with no paging.
- Rejecting a mentor does not touch their existing Hustles by design. There is
  no admin control to pause or reassign those Hustles yet.

Open product question
---------------------
KT.md says full mentor details may be revealed to the candidate after approval.
The code still anonymises the mentor inside the Hustle workspace for candidates.
Decide which behaviour is correct, then make the code and KT agree.

Local setup
-----------
  docker compose up -d
  npm install
  npm run db:deploy
  npm run db:seed
  npm run dev

Deployment note: `npm run build` deliberately does NOT run migrations, so a
local build never needs a database. On the host, run `npm run db:deploy`
before `npm run build`.
